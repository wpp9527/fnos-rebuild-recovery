# 自动备份到 GitHub 与 TrueNAS 设计稿（2026-04-22）

## 1. 目标

为当前家庭/运维服务环境设计一套稳定、可恢复、可持续扩展的自动备份方案，将关键配置与脚本同时备份到：
- GitHub 私有仓库
- TrueNAS 专用数据集（通过 NFS 挂载目录）

本期目标：
- 为配置类内容建立标准备份目录
- 自动生成可追踪、可恢复的备份副本
- 将文本配置版本化保存到 GitHub
- 将完整配置快照同步到 TrueNAS

本期不做：
- 不备份媒体文件、下载数据等大体积业务数据
- 不把 secrets 明文直接提交到 GitHub
- 不在第一版引入复杂的数据库热备体系

---

## 2. 设计结论

采用：**本机标准备份目录 + 定时双备份**。

具体模式：
1. 先在本机生成统一的标准备份目录
2. 再由定时任务分别执行：
   - 推送到 GitHub
   - 同步到 TrueNAS NFS 挂载目录

选择该模式的原因：
- 先本地收敛，再分别发布，结构清晰
- 某一目标端失败时，不会影响本地标准备份生成
- 便于排查问题与手动恢复
- 适合后续逐步扩展更多备份对象

---

## 3. 备份对象范围

本方案只覆盖**配置与关键脚本层**。

### 3.1 导航页 / 门户
- Homarr 配置
- 分组配置
- 自定义链接配置
- 与导航页相关的自定义资源（如小型图标/文档）

### 3.2 容器编排
- Docker Compose 文件
- Stack 文件
- 非敏感 `.env` 模板
- 容器部署说明

### 3.3 网络与入口配置
- Lucky / 反向代理配置
- EasyTier 配置
- DDNS 相关说明文件或脚本
- 网络映射说明

### 3.4 OpenClaw 相关
- 工作区关键脚本
- 设计文档
- 部署/维护脚本
- 非敏感配置与辅助说明

### 3.5 说明文档
- 服务清单
- 恢复文档
- 目录结构说明
- 维护说明

---

## 4. 本期明确排除项

以下内容不进入本期自动备份范围：
- 媒体文件
- 下载数据
- 缓存
- 日志
- 大型数据库原始数据
- 临时文件
- secrets 明文

排除原因：
- 体积过大，不适合 GitHub
- 恢复粒度不同，应独立设计
- 与“配置级恢复”目标不一致

---

## 5. 本机标准备份目录设计

建议建立统一标准备份目录，例如：

`/volume1/backup-config/current/`

目录结构建议如下：

```text
current/
  homarr/
  docker/
  proxy/
  network/
  openclaw/
  docs/
```

各目录职责：
- `homarr/`：导航页配置与资源
- `docker/`：compose、stack、env 模板
- `proxy/`：反代与入口配置
- `network/`：EasyTier/DDNS/网络说明
- `openclaw/`：工作区脚本、设计文档、部署脚本
- `docs/`：恢复说明、服务清单、备份说明

设计目的：
- 为 GitHub 与 TrueNAS 提供统一来源
- 降低不同路径散落导致的维护成本
- 让恢复时按类别快速定位

---

## 6. GitHub 备份策略

GitHub 用于保存：**文本配置版本历史**。

### 6.1 仓库定位
建议使用独立的**私有仓库**保存备份内容。

### 6.2 备份内容
GitHub 只同步适合版本管理的内容：
- 配置文件
- Compose / Stack 文件
- `.env` 模板
- 脚本
- 文档

### 6.3 排除策略
必须排除：
- secrets 明文
- 大型二进制文件
- 缓存与日志
- 自动生成但无版本价值的临时文件

### 6.4 提交方式
建议每次自动备份时：
- 检测变更
- 仅在有变更时提交
- 使用标准 commit message

示例：
- `backup: synology config snapshot 2026-04-22 23:30`

### 6.5 GitHub 的职责
- 保留文本配置变更历史
- 便于 diff 与回滚
- 作为异地版本化副本

---

## 7. TrueNAS 备份策略

TrueNAS 通过 **NFS 挂载目录** 接收备份，并保存到专用数据集。

### 7.1 存储结构
建议在挂载的数据集中维护两类内容：
- `current/`：当前镜像副本
- `archives/`：按日期保存的归档副本

示例：

```text
truenas-backup/
  current/
  archives/
    2026-04-22/
    2026-04-29/
```

或采用压缩归档形式：

```text
archives/
  backup-2026-04-22-2315.tar.gz
```

### 7.2 TrueNAS 的职责
- 存当前完整配置镜像
- 存按时间切分的归档快照
- 作为局域网内的大容量恢复源

### 7.3 保留策略
第一版建议：
- 每日归档
- 保留最近 14~30 份

后续可升级为：
- 最近 7 天每日
- 最近 4 周每周
- 最近 3 个月每月

---

## 8. 自动化流程设计

建议拆分为三步，而不是单个巨型脚本。

### 步骤 1：收集
从各个真实路径中提取配置并整理到标准备份目录。

要求：
- 可重复执行
- 幂等
- 有清晰日志

### 步骤 2：发布到 GitHub
从标准备份目录中筛选适合版本化的内容，提交并推送到 GitHub 私有仓库。

要求：
- 支持无变更跳过
- 严格排除 secrets
- 失败时输出明确错误

### 步骤 3：同步到 TrueNAS
将标准备份目录同步到挂载的数据集，并按策略生成归档。

要求：
- `current/` 始终代表最新可恢复状态
- 归档生成与清理逻辑清晰
- 挂载失效时不破坏本地标准备份目录

---

## 9. 调度策略

建议至少设计两档计划任务：

### 9.1 每日轻备份
执行内容：
- 更新标准备份目录
- 推 GitHub
- 更新 TrueNAS `current/`

### 9.2 每周归档备份
执行内容：
- 基于标准备份目录生成归档
- 存入 TrueNAS `archives/`
- 清理过旧归档

调度原则：
- 日常版本追踪频繁
- 重归档频率适中
- 将“当前镜像”和“历史归档”分离

---

## 10. 安全与风险控制

### 10.1 Secrets 管理
GitHub 绝不直接保存：
- API Token 明文
- 私钥
- 明文密码
- 包含敏感字段的完整 `.env`

建议方式：
- 用模板文件替代敏感 `.env`
- 对敏感项做占位符替换
- 恢复文档中单独说明 secrets 注入位置

### 10.2 失败隔离
- GitHub 推送失败，不应阻塞 TrueNAS 归档
- TrueNAS 挂载失败，不应阻塞本地标准备份生成
- 任一阶段失败，都应保留日志并能独立重试

### 10.3 恢复友好性
设计要让恢复过程可预测：
- 当前版本从哪里恢复
- 历史快照从哪里恢复
- 哪些文件需要手动补 secrets

---

## 11. 可用性与成功标准

本方案完成后，应满足：
- 任意一次配置调整后，最多 1 天内存在可恢复版本
- GitHub 上能看到配置变更历史
- TrueNAS 上有当前镜像与历史归档
- 备份失败时，不会导致整条链路静默失效
- 恢复时能按文档快速找到目标文件与目录

---

## 12. 实施建议顺序

建议按以下顺序落地：

1. 明确最终纳入的源目录清单
2. 建立本机标准备份目录结构
3. 完成收集逻辑
4. 完成 GitHub 备份逻辑
5. 完成 TrueNAS NFS 同步与归档逻辑
6. 添加定时调度
7. 编写恢复说明与排错说明

此顺序可以确保：
- 先有标准源
- 再分别对接外部目标
- 最后再自动化

---

## 13. 当前确认结论

已确认的设计决策：
- 范围：整套服务配置备份（不含大体积业务数据）
- 模式：本机标准备份目录 + 定时双备份
- TrueNAS：通过 NFS 挂载目录接收，备份到专用数据集
- GitHub：保存文本配置版本历史
- TrueNAS：保存 current + archives
- 调度：每日轻备份 + 每周归档

本设计稿已可作为后续实施依据。
