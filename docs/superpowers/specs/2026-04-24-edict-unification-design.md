# edict 统一架构与 16 岗位优化设计

日期：2026-04-24
状态：草案 v1（基于本轮确认）

## 1. 目标

将当前 edict / OpenClaw 体系统一为一套职责清晰、单一真源、流程可治理、岗位可复用的正式架构。

核心目标：
- OpenClaw 作为执行真源层
- edict 作为入口层、看板展示层、流程观察层
- OpenClaw 定义变更可同步到 edict
- 复杂任务按三省六部治理流程流转
- 16 岗位边界清晰，专业任务交给专业岗位
- 岗位能力以动态补能为主，不做全员同配

---

## 2. 总体架构定位

### 2.1 OpenClaw

定位：执行真源层。

负责：
- 任务创建与执行
- 状态迁移
- agent / session 调度
- revision / flow / wait / owner / linkedTasks
- 执行事件与结果记录
- 角色与流程定义真源

### 2.2 edict

定位：入口层 + 看板展示层 + 流程观察层。

负责：
- 飞书等入口接入
- 任务入口请求生成
- 治理语义呈现
- 看板展示
- 流程节点观察
- 审计与回放视图

说明：
- edict 可以生成任务请求
- 但 canonical task 必须落到 OpenClaw
- edict 不持有执行主状态真源

### 2.3 同步原则

原则：
- 任务事实、状态事实、角色定义事实，以 OpenClaw 为真源
- edict 负责展示方式与观察视图
- OpenClaw 定义变化应同步投影到 edict

## 3. main 与 taizi 关系

正式定义：
- `main == taizi`
- 运行时名称：`main`
- 治理展示名称：`taizi / 太子`

含义：
- 不再维持两个独立职责中心
- 所有任务统一从 `main` 进入
- 在治理语义上，这一步等于太子接旨

展示建议：
- 对外展示优先显示“太子”
- `main` 仅保留运行时技术标识语义

## 4. 复杂任务判定与流程进入规则

### 4.1 复杂度评分

建议按以下维度打分：
- 是否跨 2 个以上模块
- 是否跨 2 个以上角色
- 是否需要拆子任务
- 是否有兼容/迁移风险
- 是否需要审议/复核
- 是否影响线上主链路

每项 0/1 分。

### 4.2 判定规则

- 0~1 分：简单任务，可短链处理
- >= 2 分：进入治理流程 `governance-flow`

### 4.3 强制进入治理流程的情形

满足任一条件直接进入：
- 用户明确要求走流程/审议/留痕
- 任务涉及架构、流程、角色、治理规则变更
- 任务涉及多岗位协同
- 执行中出现风险升级，需要重新审议

---

## 5. 治理主链

复杂任务必经链：
- `taizi/main`
- `zhongshu`
- `menxia`
- `shangshu`

职责分工：
- 太子：接旨立项、意图提炼、复杂度判定、最终回奏
- 中书省：理解目标、拆解任务、设计方案
- 门下省：审议把关、质量闸门、通过/不通过判断
- 尚书省：分派、协调、跟踪、回收、汇总

### 5.1 结果回流

执行完成后：
- 先回 `shangshu`
- 再由尚书省汇总
- 最终回到 `taizi`
- 太子向用户做大白话回奏

### 5.2 回奏风格

不使用固定模板，要求：
- 大白话
- 直接汇报
- 一眼能懂

但内容必须说清：
- 做完没
- 大概什么时候完成
- 结果是什么
- 中途有没有关键变更
- 有没有尾巴/遗留问题
- 现在是否还需要用户决定什么

## 6. 安全与合规重审规则

制度：

> 凡安全条件、合规条件、权限条件、供应链条件发生变化，原方案自动失效，必须退回中书省按新条件重写，并重新经过审议后方可执行。

### 6.1 刑部

定位：常规安全 / 合规 / 审计审查岗。

规则：
- 一旦提出风险或整改建议
- 原方案自动失效
- 必须退回中书省重写方案
- 再走门下审议与尚书分派

### 6.2 锦衣卫

定位：高敏强审岗、供应链与权限红线岗。

特权：
- 优先插队审查权
- 必要时可阻断任务继续流转

触发条件（命中任一项自动触发）：
- 新增或修改外部入口
- 接触密钥、token、凭证
- 高权限配置或执行变更
- 引入第三方依赖或供应链组件
- 涉及敏感数据流转
- 存在越权或对外暴露风险
- 用户明确要求强安全审查

阻断规则：
- 一旦阻断或提出强约束条件
- 默认退回中书省
- 由中书省按最新安全条件改写方案
- 再经门下省重新审议后执行

## 7. 16 岗位正式优化版

### 7.1 主链 4 岗

#### 太子 / main
- 统一入口
- 接旨立项
- 意图提炼
- 复杂度判定
- 最终回奏

#### 中书省
- 方案设计
- 任务拆解
- 执行路径规划
- 风险与依赖整理
- 被退回后的方案改写

#### 门下省
- 质量闸门
- 审议把关
- 不通过项识别
- 风险说明
- 通过/不通过结论

#### 尚书省
- 总调度
- 分派岗位
- 进度协调
- 结果回收
- 阶段/最终汇总

### 7.2 核心执行岗 6 岗

#### 兵部
只负责：
- 业务代码
- 功能实现
- Bug 修复
- 算法与逻辑

明确不负责：
- Docker
- 部署
- CI/CD
- 容器编排
- 环境搭建
- 发布回滚

#### 工部
只负责：
- 基础设施
- Docker / Compose / 容器配置
- CI/CD
- 部署与回滚
- 环境配置
- 自动化交付

明确不负责：
- 业务功能代码
- 产品逻辑修改
- 业务层 Bug 修复

#### 刑部
- 常规安全审查
- 合规检查
- 审计意见
- 风险等级与整改建议
- 一旦提出风险或整改建议，触发方案重审

#### 礼部
- 文档成稿
- API 文档
- 规范说明
- 报告与汇报材料
- 交接文档

说明：
- 中书省负责方案规划
- 礼部负责文档成稿与表达

#### 户部
- 通用数据分析
- 指标统计
- 报表
- 一般成本分析

不负责：
- token / 流量 / 配额主责治理

#### 吏部
- Agent 注册与归档
- 权限边界治理
- 角色职责校验
- 使用规范
- 培训材料

### 7.3 扩展专岗 6 岗

#### 钦天监 / 早朝官
- 晨报 / 日报 / 周报
- 定时播报
- 异常播报
- 关键变化提醒
- 风险/告警事件摘要

#### 度支司
定位：资源用量治理与精细核算主责岗位。

负责：
- token 用量统计
- API 调用量统计
- 外部流量与额度统计
- 资源消耗归因
- 配额建议
- 资源使用异常识别
- 精细成本/资源治理

不负责：
- 通用经营报表
- 任务调度
- 执行分派

#### 太学寺
- 大输入预处理
- 长上下文压缩
- 材料整编
- 规范化输入包生成

#### 锦衣卫
- 高权限变更审查
- 凭证 / 密钥 / token 风险审查
- 外部入口接入审查
- 供应链依赖审查
- 越权 / 误用 / 滥用面检查
- 阻断 / 放行意见

#### 情报使
- 外部资料检索
- 来源汇总
- 竞品/方案/背景对比
- 研究摘要

#### 技能导师
定位：能力治理与补能中枢。

负责：
- 能力缺口识别
- skill / 工具 / 方法推荐
- 学习路径设计
- task-skill 匹配
- 岗位能力画像沉淀
- 补能策略与经验模板沉淀

说明：
- 不替代执行岗位亲自完成专业工作
- 重点在“让原岗位能做成”

## 8. 分派矩阵

### 固定主链
- 新任务 → 太子/main
- 方案规划 → 中书省
- 审议把关 → 门下省
- 分派与汇总 → 尚书省

### 专业岗触发
- 业务代码 / 功能 / bug / 算法 → 兵部
- Docker / 部署 / 流水线 / 环境 / 自动化 → 工部
- 常规安全 / 合规 / 审计 → 刑部
- 高敏权限 / 密钥 / 外部入口 / 供应链 → 锦衣卫
- 文档 / 规范 / 报告 → 礼部
- 数据 / 指标 / 报表 / 粗粒度成本 → 户部
- token / API / 流量 / 配额 / 精细资源治理 → 度支司
- Agent 管理 / 权限编制 / 培训 → 吏部
- 长输入 / 大文档 / 材料整编 → 太学寺
- 外部检索 / 资料收集 → 情报使
- 晨报 / 定时摘要 / 异常播报 → 钦天监
- 缺技能 / 需补能 → 技能导师

## 9. skill 机制

### 9.1 基本原则
- 岗位专属为主，不做全员同配
- 技能以动态临时挂载为主
- 缺能力时优先自学，再执行
- 仍无法完成再上报

### 9.2 能力模型
- 岗位固有能力：来自角色职责本身
- 岗位基础 skill：少量必要常驻能力
- 任务临时 skill：按任务命中场景临时加载

### 9.3 自学规则
- 岗位接到任务先判断是否能做
- 若缺工具/缺方法/缺 skill：先学习、补能
- 学后继续执行
- 仍失败才上报尚书省或回流上级
